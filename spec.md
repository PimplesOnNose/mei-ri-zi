## 1. Data Schemas

### 1.1 hsk_daily.json — Master Word List

The single data file the frontend reads. Generated by `scripts/generate_data.py`.
One entry per word, ordered by HSK level then by frequency within the level.
The flat array index IS the day offset — word at index 0 is Day 1 for any learner.

```json
{
  "meta": {
    "title": "每日字",
    "title_en": "Mei Ri Zi",
    "version": "1.0",
    "hsk_revision": "3.0 (2021)",
    "total_words": 10898,
    "levels": [
      { "id": "prep",  "name": "入门",  "element": "天水", "color": "#e8e8ec", "word_count": 0 },
      { "id": "hsk1",  "name": "HSK 1", "element": "木",   "color": "#4a9e8a", "word_count": 300 },
      { "id": "hsk2",  "name": "HSK 2", "element": "木→火", "color": "#6db3a4", "word_count": 197 },
      { "id": "hsk3",  "name": "HSK 3", "element": "火",   "color": "#c4452d", "word_count": 493 },
      { "id": "hsk4",  "name": "HSK 4", "element": "火→土", "color": "#c9a96e", "word_count": 990 },
      { "id": "hsk5",  "name": "HSK 5", "element": "土→金", "color": "#d4b878", "word_count": 1579 },
      { "id": "hsk6",  "name": "HSK 6", "element": "金",   "color": "#8faacc", "word_count": 1777 },
      { "id": "hsk79", "name": "HSK 7-9", "element": "水", "color": "#3a6e8e", "word_count": 5562 }
    ],
    "stems": ["甲","乙","丙","丁","戊","己","庚","辛","壬","癸"],
    "stem_elements": ["木","木","火","火","土","土","金","金","水","水"],
    "generated_at": "2026-07-27T00:00:00Z"
  },
  "words": [
    {
      "id": "hsk1_0001",
      "hsk_level": 1,
      "word": "你好",
      "pinyin_text": "nǐhǎo",
      "pinyin_tones": [3, 3],
      "pinyin_parts": ["nǐ", "hǎo"],
      "pos": "greeting",
      "english": "hello",
      "radicals": ["亻", "子"],
      "components": [
        { "char": "你", "role": "semantic", "meaning": "you" },
        { "char": "好", "role": "compound", "meaning": "good", "breakdown": "女 (woman) + 子 (child)" }
      ],
      "stroke_count": 12,
      "example": {
        "zh": "你好，我是小明。",
        "pinyin": "Nǐ hǎo, wǒ shì Xiǎomíng.",
        "pinyin_parts": ["Nǐ", "hǎo", "wǒ", "shì", "Xiǎo", "míng"],
        "pinyin_tones": [3, 3, 3, 4, 3, 2],
        "en": "Hello, I am Xiaoming."
      }
    }
  ]
}
```

**Notes:**
- `pinyin_tones` is an array of integers (1–4 for lexical tones, 0 for neutral),
  one per **pinyin syllable** (not per character — for most Chinese words these
  are the same, but for multi-character words each character produces exactly one
  syllable). Used for tone-colored rendering (§3).
- `pinyin_parts` is the pinyin split **per syllable**, with tone marks already applied.
  The frontend iterates `pinyin_parts` and `pinyin_tones` in parallel — same length,
  same indexing — to render each syllable with its tone color class.
- The `example` object also contains `pinyin_parts` and `pinyin_tones` arrays
  for the example sentence pinyin, applied with tone colors the same way.
- `components` is the radical/component breakdown for the glyph section (§5.4).
  Each component has a `role` ("semantic", "phonetic", "compound") and `meaning`.
- `stroke_count` is the total strokes for the word (sum of per-character counts).
  Used by hanzi-writer quiz feedback (§5.5).
- Audio paths are NOT in this file. Audio is resolved via `audio/index.json` (§7.3).

### 1.2 audio/index.json — Audio Path Map

Generated by `scripts/generate_audio.py`. Maps word IDs to audio file paths.

```json
{
  "version": 1,
  "generated_at": "2026-07-27T00:00:00Z",
  "files": {
    "hsk1_0001": {
      "word": "audio/word_audio/hsk1_0001/word.mp3",
      "sentence": "audio/word_audio/hsk1_0001/sentence.mp3"
    },
    "hsk1_0002": {
      "word": "audio/word_audio/hsk1_0002/word.mp3"
    }
  }
}
```

**Notes:**
- Only words that have been generated appear in the map.
- Missing entries show "audio 未生成" — run `scripts/generate_audio.py` to batch-generate.
  The frontend falls back gracefully with "audio unavailable" if the file doesn't exist.
- The frontend loads this file once on app init and caches it in memory.

### 1.3 localStorage Contracts

All user state lives in `localStorage`. Four keys:

#### `mei-ri-zi/state` — Primary state blob

```json
{
  "version": 1,
  "schema": "mei-ri-zi/state",
  "created_at": "2026-03-15T08:12:00Z",
  "learner": {
    "start_date": "2026-03-15",
    "start_offset": 0,
    "timezone": "Asia/Shanghai"
  },
  "progress": {
    "last_opened_date": "2026-05-04",
    "current_hsk_level": 2,
    "words_seen": ["hsk1_0001", "hsk1_0002"],
    "completed_jiazi_cycles": 0,
    "daily_pillar_completed": { "shi": false, "xie": false, "xi": false }
  },
  "favorites": ["hsk1_0003"],
  "srs": [
    {
      "id": "hsk1_0001",
      "word": "你好",
      "pinyin": "nǐhǎo",
      "english": "hello",
      "level": 1,
      "ease": 2.5,
      "interval": 0,
      "nextReview": 1711929600000,
      "repetitions": 0,
      "lastWritingScore": null
    }
  ],
  "writing_cursor": {
    "word_id": "hsk2_0197",
    "char_idx": 0
  },
  // Transient fields (appended to progress during catch-up, not present in rest state):
  // "catchup_days_remaining": 3   — see §5.8
  "settings": {
    "audio_speed": 0.95,
    "tone_colors": true,
    "seasonal_atmosphere": true,
    "reveal_translation": false,
    "write_all_chars": true,
    "language": "en"
  }
}
```

**Field notes:**
- `learner.start_date` — set once on first visit, never changes. ISO date string.
- `learner.start_offset` — default 0. Set to the cumulative word count of preceding
  levels when the learner chooses to skip ahead (e.g., "start at HSK 3" → offset = 300+197 = 497).
- `current_word_index` — computed on each app load as `today - start_date + start_offset`.
  Not stored persistently — derived from `last_opened_date`, `start_date`, and `start_offset`.
- `progress.words_seen` — array of word IDs the learner has opened at least once.
  Grows monotonically. Basis for the Five-Colored Earth mastery bar (§4).
  Over the full curriculum this reaches ~10,898 entries — trivially small in
  storage (~500KB as JSON) but the serialization cost grows linearly on each
  save. **Optimization:** store as a `Set` in memory and serialize as a
  sorted array only on writes. For altar bar renders, derive per-tier counts
  via the pre-computed `wordTierMap` rather than iterating `words_seen`.
  **Debounce:** `saveState()` should use a 30-second debounce plus flush on
  `beforeunload` — so rapid interactions (favorite toggling, pillar completions)
  don't re-serialize the full array on every click.
- `progress.daily_pillar_completed` — reset each day. Tracks which pillars of today's
  识写习 loop have been completed. Keys: `shi` (识), `xie` (写), `xi` (习).
- `srs` — the full SRS deck. Each item matches the `SRSItem` type (§6.1).
  `lastWritingScore` is `null` if the word hasn't been practiced in 写 yet,
  otherwise an integer (totalMistakes from hanzi-writer quiz).
- `streak` **is not stored in this key.** See `mei-ri-zi/streak` (§1.3) for streak data.
- `writing_cursor` — persists the learner's position in the 写 phase so a reload resumes
  at the correct character. Stores `word_id` (not `day_offset`) so navigation between
  days doesn't leave stale cursor data. Only applies when the current day's word
  matches `writing_cursor.word_id`; otherwise the cursor is treated as stale and reset
  to `char_idx: 0`.

#### `mei-ri-zi/daily` — Daily activity counters (auto-reset, reserved for v2)

```json
{
  "date": "2026-05-04",
  "new_words": 1,
  "reviews_done": 3,
  "writing_chars": 2,
  "pillar_completions": 1  // number of daily pillars (识写习) completed today
}
```

Reset automatically when `date` !== today. Incremented by the 识写习 loop.
**v1 note:** This key is written to but not consumed by any v1 UI component.
Reserved for v2 analytics (weekly summaries, practice stats, streak heatmap).

#### `mei-ri-zi/streak` — Streak data (separate from main state for atomic updates)

```json
{
  "last_active_date": "2026-05-04",
  "current_streak": 12,
  "longest_streak": 23
}
```

#### `mei-ri-zi/audio-cache` — Tracks which audio files have been generated

```json
{
  "generated": ["hsk1_0001", "hsk1_0002", "hsk1_0003"]
}
```

Used by the audio playback flow (§7.4).

#### `mei-ri-zi/version` — Schema migration marker

```json
{
  "version": 1
}
```

Read once on app init. If the stored schema version (`mei-ri-zi/state.version`)
is less than the current app version, a migration function runs before any
other operation:

```javascript
function migrateState(state, targetVersion):
    while state.version < targetVersion:
        state = MIGRATIONS[state.version](state)
        state.version += 1
    return state
```

Each migration is a pure function `(oldState) => newState` that adds default
values for new fields. MIGRATIONS is a version-keyed map. Adding v2 fields
is a matter of appending to the map — existing v1 states migrate forward
without data loss.

## 2. Personal Timeline Engine

### 2.1 Day Offset Computation

```
function getDayOffset(state):
    today = new Date().toLocaleDateString('sv-SE')  // "YYYY-MM-DD" (local time)
    startDate = state.learner.start_date             // "YYYY-MM-DD"
    daysDiff = dateDiffInDays(startDate, today)      // integer, >= 0
    return daysDiff + state.learner.start_offset
```

`dateDiffInDays(a, b)` computes `(parseDate(b) - parseDate(a)) / 86400000`, floored.
Returns 0 on first visit (same day as start_date).

**Note:** Using `toLocaleDateString('sv-SE')` instead of `toISOString()` ensures the
computed date is in the learner's local timezone, not UTC. A learner opening the
app at 11pm in New York sees today's word, not tomorrow's.

**Timezone change during travel:** All dates use the device's current local
zone. If a learner flies from Shanghai to New York, their "today" shifts by
~12 hours. The personal timeline doesn't retroactively adjust — the next app
load computes `dateDiffInDays(last_active_date, new_local_today)`. A single
forward timezone jump may skip a calendar day (appears as a missed day); a
backward jump won't double-count because `last_active_date` is stored as a
YYYY-MM-DD string, not a timestamp. This is acceptable: no server involvement
and no timezone database dependency.

### 2.2 Word Resolution

```
function getTodayWord(dayOffset, hskDaily):
    if dayOffset < 0 or dayOffset >= hskDaily.words.length:
        return null  // out of range — show "恭喜！你已完成所有每日字"
    return hskDaily.words[dayOffset]
```

The word at `hskDaily.words[dayOffset]` is deterministic for any given offset.
Two learners on their respective Day 47 always see the same word.

### 2.3 Heavenly Stem Badge

```
HEAVENLY_STEMS = ["甲","乙","丙","丁","戊","己","庚","辛","壬","癸"]
STEM_ELEMENTS  = ["木","木","火","火","土","土","金","金","水","水"]
STEM_COLORS    = ["#4a9e8a","#4a9e8a","#c4452d","#c4452d","#c9a96e","#c9a96e","#8faacc","#8faacc","#3a6e8e","#3a6e8e"]

function getStemBadge(dayOffset):
    stemIndex = dayOffset % 10
    weekNumber = Math.floor(dayOffset / 10) + 1
    stem = HEAVENLY_STEMS[stemIndex]
    element = STEM_ELEMENTS[stemIndex]
    color = STEM_COLORS[stemIndex]
    return {
        stem: stem,                      // "甲"
        week: weekNumber,                // 5
        label: `${stem}·初${weekNumber}`, // "甲·初5"
        element: element,                // "木"
        color: color                     // "#4a9e8a"
    }
```

### 2.4 甲子 Cycle Detection

```javascript
function checkJiaziCompletion(state):
    dayOffset = getDayOffset(state)
    // (dayOffset + 1) because dayOffset is 0-indexed (Day 1 = offset 0)
    // Day 60  → offset 59  → (59 + 1)  % 60 == 0 ✓ fires on day 60
    // Day 120 → offset 119 → (119 + 1) % 60 == 0 ✓ fires on day 120
    if dayOffset > 0 and (dayOffset + 1) % 60 == 0:
        state.progress.completed_jiazi_cycles += 1
        triggerYellowDragonCelebration()
```

Called once per app load. The Yellow Dragon celebration (§8.5) fires only once per
completed cycle. The `completed_jiazi_cycles` counter prevents re-firing on reload.

**Timing note:** The celebration fires when the learner opens the app on their
personal **Day 60** (offset = 59). The stem badge that day reads "癸·初6"
(offset 59 = stem-index 9 = 癸, week 6) — the last day of the completed cycle.
The celebration honors the 60 days completed, and the learner begins the next
甲子 on Day 61 with badge "甲·初7". The celebration marks the completed cycle,
not the boundary — so it falls on day 60 itself.

### 2.5 HSK Level Resolution

```javascript
LEVEL_BOUNDARIES = [
    { level: "prep",  start: -1,   end: -1 },  // no-op placeholder: 0 words, never matches
    { level: "hsk1",  start: 0,    end: 299 },
    { level: "hsk2",  start: 300,  end: 496 },
    { level: "hsk3",  start: 497,  end: 989 },
    { level: "hsk4",  start: 990,  end: 1979 },
    { level: "hsk5",  start: 1980, end: 3558 },
    { level: "hsk6",  start: 3559, end: 5335 },
    { level: "hsk79", start: 5336, end: 10897 }
]

function getHSKLevel(dayOffset):
    for each boundary in LEVEL_BOUNDARIES:
        if dayOffset >= boundary.start and dayOffset <= boundary.end:
            return boundary
    return LEVEL_BOUNDARIES[LEVEL_BOUNDARIES.length - 1]  // fallback: hsk79
```

Returns the level object with `level`, `start`, `end`. Used to determine the
Wu Xing color for the card accent, the stroke color for hanzi-writer, and the
Five-Colored Earth altar band to highlight.

## 3. Cultural Color System — CSS Variables

### 3.1 Wu Xing HSK Palette

```css
:root {
  /* HSK Level Colors (Wu Xing Named Pigments) */
  --hsk-prep:  #e8e8ec;  /* 月白 yuèbái — heavenly water */
  --hsk1:      #4a9e8a;  /* 青草 qīngcǎo — wood */
  --hsk2:      #6db3a4;  /* 翠微 cuìwēi — wood→fire */
  --hsk3:      #c4452d;  /* 朱砂 zhūshā — fire */
  --hsk4:      #c9a96e;  /* 赭石 zhěshí — fire→earth */
  --hsk5:      #d4b878;  /* 缃色 xiāngsè — earth→metal */
  --hsk6:      #8faacc;  /* 月白银 yuèbái-yín — metal */
  --hsk79:     #3a6e8e;  /* 天青 tiānqīng — water */

  /* Tone Colors (Five-Colored Pinyin) */
  --tone-1-metal:   #c8c8d0;  /* 1st tone — silver, steady */
  --tone-2-wood:    #5fb388;  /* 2nd tone — green, rising */
  --tone-3-earth:   #c9a96e;  /* 3rd tone — ochre, dipping */
  --tone-4-fire:    #c4452d;  /* 4th tone — vermillion, falling */
  --tone-0-water:   #3a4858;  /* neutral — ink, still */

  /* Tone Color Contrast Resolution
     On the dark scholar's-ink background (--bg: #0a0a14, --bg-card: #121422),
     the darker tone colors risk failing WCAG AA (4.5:1) for body-sized pinyin:

       --tone-0-water: #3a4858 on #121422  → contrast ratio ~3.8:1 (FAILS AA)
       --tone-4-fire:  #c4452d on #121422  → contrast ratio ~4.0:1 (FAILS AA)

     Resolution — use lighter variants as the DEFAULT tone colors for pinyin,
     reserving the richer originals as the canonical reference for export cards
     and lighter backgrounds:

       --tone-0-water-light : #5a7898  (contrast ~5.2:1 on #121422 — passes AA)
       --tone-4-fire-light  : #d4654d  (contrast ~4.8:1 on #121422 — passes AA)

     The CSS classes use these safe variants by default. A CSS custom property
     override (`.rich-mode`) swaps back to the canonical colors for contexts
     where contrast is not a concern.

     The text-shadow approach (glow behind the tone span) is NOT used as a
     primary fix because it varies across browsers, fails in Windows High
     Contrast Mode, and does not help with ::selection color.
  */
  --tone-0-water:   #5a7898;  /* pinyin default — lighter, passes AA */
  --tone-4-fire:    #d4654d;  /* pinyin default — lighter, passes AA */
  /* Canonical rich variants (for export/light-background use):
     --tone-0-water-rich: #3a4858;
     --tone-4-fire-rich:  #c4452d;
  */

  /* Five-Colored Earth Altar
     Canonical Wu Xing soil colors from the 社稷坛 (Altar of Earth and Harvest):
     green East, red South, yellow Center, white West, black North.

     NOTE — these are NOT the same as the per-HSK-level card accent colors (--hsk1..--hsk79).
     The altar collapses 9 HSK tiers into the canonical 5 elements:
       Wood  = HSK 1-2   (--altar-east   ~= --hsk1/#4a9e8a, since HSK 1 is pure Wood)
       Fire  = HSK 3-4   (--altar-south ~= --hsk3/#c4452d, since HSK 3 is pure Fire)
       Earth = HSK 5     (--altar-center #c9a96e, --hsk5 uses the gradient color 缃色/#d4b878)
       Metal = HSK 6     (--altar-west  ~= --hsk6/#8faacc, silver)
       Water = HSK 7-9   (--altar-north ~= --hsk79/#3a6e8e, deep water)
     The earth band uses the canonical Five-Color-Earth yellow (#c9a96e 旅石),
     NOT the HSK 5 gradient color (#d4b878 缃色). This is intentional: the altar
     honors the literal soil colors of the Ming altar, while the card accent
     honors the HSK-level intermediary-color progression. Do not "unify" these
     without re-reading plan.md §2.1 and §2.6.
  */
  --altar-east:     #4a9e8a;  /* green — wood */
  --altar-south:    #c4452d;  /* red — fire */
  --altar-center:   #c9a96e;  /* yellow — earth */
  --altar-west:     #8faacc;  /* white/silver — metal */
  --altar-north:    #3a6e8e;  /* black/blue — water */

  /* Dark Base (scholar's ink-night palette, inspired by eight-flavors night theme)
     Warm parchment-on-deep-ink contrast for a classical Chinese literati feel.
     Avoids cold/bluish dark modes — the warmth makes long reading sessions gentler. */
  --bg:            #0a0a14;  /* deep ink night — like aged ink-stone */
  --bg-card:       #121422;  /* card — subtle warmth from the parchment fg */
  --bg-elevated:   #171a2e;  /* elevated surface — modal, settings panel */
  --bg-surface:    #1c1f34;  /* input fields, search bar */
  --bg-glow:      radial-gradient(120% 80% at 18% 0%, rgba(244,236,216,0.03), transparent 50%),

  --border:        rgba(240, 232, 213, 0.12);  /* hairline borders */
```

### 3.4 Typography Scale

Font stack sourced from `yueli` to maintain visual coherence across projects.
The idiom/word character uses **Ma Shan Zheng** — a Chinese brush calligraphy font
that gives each character the weight of hand-written brushwork.

```css
:root {
  --font-display-zh: 'Ma Shan Zheng', 'Noto Serif SC', serif;
  --font-body-zh:    'Noto Serif SC', 'Songti SC', serif;
  --font-display-en: 'Cormorant Garamond', 'Times New Roman', serif;
  --font-body-en:    'Cormorant Garamond', Georgia, serif;
  --font-pinyin:     'Cormorant Garamond', 'Inter', sans-serif;
  --font-ui:         'Inter', -apple-system, system-ui, sans-serif;
}
```

| Token | Font | Size | Weight | Letter Spacing | Use |
|-------|------|------|--------|---------------|-----|
| `display-zh` | Ma Shan Zheng | 48px (64px desktop) | 400 | 0.1em | Daily word character (识 card) |
| `body-zh` | Noto Serif SC | 18px | 400 | 0.05em | Example sentences, glyph breakdown |
| `display-en` | Cormorant Garamond | 18px | 500 | — | Section headings, English labels |
| `body-en` | Cormorant Garamond | 16px | 400 | — | English translations, meanings |
| `pinyin` | Cormorant Garamond italic | 16px | 400 | 0.02em | Pinyin annotations |
| `ui` | Inter | 13–14px | 500 | — | Buttons, nav, settings, labels |

**Google Fonts import:**
```html
<link href="https://fonts.googleapis.com/css2?family=Ma+Shan+Zheng&family=Noto+Serif+SC:wght@300;400;500;700&family=Cormorant+Garamond:ital,wght@0,400;0,500;0,600;0,700;1,400;1,500&family=Inter:wght@400;500;600&display=swap" rel="stylesheet">
```

**Font loading strategy:**

| Concern | Mitigation |
|---------|------------|
| `display=swap` in URL | Ensures text renders in fallback font while Chinese fonts load. Already included above. |
| Ma Shan Zheng (~3.5MB woff2) | Preload with `<link rel="preload" href="..." as="font" crossorigin>` — this is the critical font for first paint (the daily character). The woff2 URL can be extracted from the Google Fonts CSS by inspecting the `@font-face` src after the page loads. |
| Noto Serif SC (~5MB full set) | Not preloaded — loads on demand after layout. Only covers example sentences and glyph breakdowns, not first paint. Consider subsetting to HSK vocabulary characters (~5000) for production. |
| Total font budget | ~9MB at worst. Acceptable for a static app loaded once, but a PWA cache (v3) would make subsequent loads instant. |

**Preload tag (add to `<head>`):**
```html
<link rel="preload" href="https://fonts.gstatic.com/s/mashanzheng/v14/...woff2" as="font" type="font/woff2" crossorigin>
<!-- ^ exact URL depends on Google Fonts CSS response — inspect at runtime and hard-code -->
```

## 4. Five-Colored Earth Altar — Mastery Progress Bar

### 4.1 Visual Design

A horizontal strip at the bottom of every screen. Five bands, one per element:

```
┌─────────────────────────────────────────────────┐
│  ■■■■■■■■░░  │  ■■■■░░░░░░  │  ░░░░░░░░░░  │  ░░░░░░░░░░  │  ░░░░░░░░░░  │
│   木 Wood     │   火 Fire     │   土 Earth    │   金 Metal    │   水 Water    │
│   HSK 1-2    │   HSK 3-4    │   HSK 5      │   HSK 6      │   HSK 7-9    │
└─────────────────────────────────────────────────┘
```

Each band fills proportionally to `words_seen_in_that_tier / total_words_in_that_tier`.
Filled portion uses the element's altar color; unfilled portion uses `--ql-border`.

### 4.2 Implementation

```javascript
// Pre-computed word-to-tier mapping, built once on data load
// Prevents iterating all 10,896 words on every altar render
let wordTierMap = null

function ensureTierMap(hskDaily):
    if wordTierMap: return
    wordTierMap = {}
    for word in hskDaily.words:
        wordTierMap[word.id] = levelToTier(word.hsk_level)

function getAltarState(wordsSeen):
    tiers = {
        wood:  { seen: 0, total: 0, color: "--altar-east" },
        fire:  { seen: 0, total: 0, color: "--altar-south" },
        earth: { seen: 0, total: 0, color: "--altar-center" },
        metal: { seen: 0, total: 0, color: "--altar-west" },
        water: { seen: 0, total: 0, color: "--altar-north" }
    }
    // Derive per-tier totals from LEVEL_BOUNDARIES (§2.5) so they stay in sync
    // automatically. Each tier spans multiple HSK levels — sum their word counts.
    tiers.wood.total  = tierWordCount(["hsk1", "hsk2"],      LEVEL_BOUNDARIES)
    tiers.fire.total  = tierWordCount(["hsk3", "hsk4"],      LEVEL_BOUNDARIES)
    tiers.earth.total = tierWordCount(["hsk5"],              LEVEL_BOUNDARIES)
    tiers.metal.total = tierWordCount(["hsk6"],              LEVEL_BOUNDARIES)
    tiers.water.total = tierWordCount(["hsk79"],             LEVEL_BOUNDARIES)

    // Now iterate words_seen (much smaller set, bounded by days since start)
    // to fill per-tier seen counts using the pre-computed wordTierMap
    for wordId in wordsSeen:
        tier = wordTierMap[wordId]
        if tier and tiers[tier]:
            tiers[tier].seen += 1

    return tiers

function tierWordCount(levelIds, boundaries):
    total = 0
    for each boundary in boundaries:
        if boundary.level in levelIds:
            total += (boundary.end - boundary.start + 1)
    return total

function levelToTier(level):
    if level <= 2: return "wood"
    if level <= 4: return "fire"
    if level == 5: return "earth"
    if level == 6: return "metal"
    return "water"
```

Rendered as five `<div>` elements with `width: 20%` each, containing an inner
`<div>` with `width: ${(seen/total)*100}%` and the tier's altar color as background.

**Note on totals:** Tier word counts are derived programmatically from
`LEVEL_BOUNDARIES` (§2.5) via `tierWordCount()`. No hard-coded numbers to drift.

### 5.2 Phase: 识 (Card)

**Before phase entry (app init, once per day):**
Check if `progress.last_opened_date !== today`. If so, reset
`daily_pillar_completed = { shi: false, xie: false, xi: false }`. This runs
once per app load, before any phase renders. Resets on the first load of each
new calendar day (local time, per §2.1).

**On enter:**
1. Resolve today's word via `getTodayWord(getDayOffset(state))`.
2. Auto-enroll word into SRS via `ensureEnrolled()` (§6.2).
3. Add word ID to `progress.words_seen` if not already present.
4. Render the card (§5.4).

**On continue (user taps "继续" or "写 →"):**
1. Set `progress.daily_pillar_completed.shi = true`.
2. Increment `daily.new_words`.
3. Transition to 写.

**On skip:**
1. Set `progress.daily_pillar_completed.shi = true` (still counts as seen).
2. Transition to 写.

### 5.3 Phase: 写 (Writing)

**On enter:**
1. Check `settings.write_all_chars`. If true, queue all characters of the word.
   If false, queue only the head character.
2. Load hanzi-writer (§5.5). Render 米字格 + first character.
3. **Writing cursor stale check** — performed on every 写 phase entry, before
   any hanzi-writer init:
   `if state.writing_cursor.word_id !== getTodayWord(dayOffset).id:`
   `    state.writing_cursor = { word_id: null, char_idx: 0 }`
   This catches three scenarios: (a) navigating to a different day and back,
   (b) first visit to 写 on a given day, (c) a previous day's stale cursor
   that was never cleaned up. If the cursor is fresh (word IDs match), restore
   `char_idx` and resume from that position.

**On character complete (quiz `onComplete`):**
1. Record `totalMistakes` as `lastWritingScore` in the SRS item for this word.
2. If more characters remain, advance `char_idx` and render next character.
3. If all characters done, set `progress.daily_pillar_completed.xie = true`.
4. Increment `daily.writing_chars` by number of characters practiced.

**On skip:**
1. Set `progress.daily_pillar_completed.xie = true`.
2. Transition to 习.

```javascript
function initWriter(containerId, char, hskLevelColor):
    container = document.getElementById(containerId)
    container.innerHTML = ""

    // Draw 米字格 SVG background
    const svg = document.createElementNS("http://www.w3.org/2000/svg", "svg")
    svg.setAttribute("width", canvasSize)
    svg.setAttribute("height", canvasSize)
    // ... draw grid lines (see plan.md §4.7 for SVG) ...
    container.appendChild(svg)

    // Create hanzi-writer instance on top of the SVG
    writer = HanziWriter.create(container, char, {
        width: canvasSize,
        height: canvasSize,
        padding: 5,
        showCharacter: true,
        showOutline: true,
        strokeColor: hskLevelColor,        // e.g., "#c4452d" for HSK 3
        radicalColor: "#4a9e8a",            // Wood green for radicals
        strokeAnimationSpeed: 1.2,
        delayBetweenStrokes: 300,
        outlineColor: "#2a2a4a",
        drawingColor: hskLevelColor,        // user's trace in level color
        drawingWidth: 6,
        highlightOnComplete: true,
        highlightColor: "#50fa7b",
        showHintAfterMisses: 3,
        charDataLoader: function(char, onComplete, onError) {
            // Try local bundle first (data/char_strokes/ — generated by a
            // build step that downloads hanzi-writer-data for each unique
            // character in the HSK word list), then fall back to CDN.
            fetch(`data/char_strokes/${char}.json`)
                .then(r => r.ok ? r.json() : null)
                .then(data => {
                    if (data) onComplete(data)
                    else HanziWriter.loadCharacterData(char).then(onComplete).catch(onError)
                })
                .catch(() => {
                    HanziWriter.loadCharacterData(char).then(onComplete).catch(onError)
                })
        }
    })
    return writer
```

### 5.8 Missed-Day Detection

```javascript
function detectMissedDays():
    // Use local-timezone date per §2.1 (UTC would mislabel days at the edges).
    // Note: streak data lives in the separate `mei-ri-zi/streak` key (§1.3),
    // NOT in the primary `mei-ri-zi/state` blob.
    today = new Date().toLocaleDateString('sv-SE')  // "YYYY-MM-DD" (local time)
    streakData = loadStreak()
    lastVisit = streakData.last_active_date
    if not lastVisit: return 0  // first visit ever
    daysMissed = dateDiffInDays(lastVisit, today) - 1
    return Math.max(0, daysMissed)
```

If `daysMissed >= 1`:
- Show notice: `你没有打开每日字 ${daysMissed} 天`
- Two buttons:
  - **补上** — add a transient `catchup_days_remaining` counter to the state
    (`state.progress.catchup_days_remaining = daysMissed`). On each "Next →" tap,
    decrement the counter and advance `day_offset` by 1 (without writing to
    `start_date` or `start_offset`). Show each missed day's 识 card only (no
    写/习 — too many to catch up on). If the app closes mid-catch-up, the
    remaining missed days are treated as skipped and the streak is lost.
  - **跳过** — do nothing. The personal timeline already accounts for elapsed time.

If `daysMissed >= 1`:
- Streak resets to 0 (unless the learner chose 补上 and walked through all
  missed days consecutively without closing the app).

**Catch-up state lifecycle:**
| Event | `catchup_days_remaining` behavior |
|-------|------------------------------------|
| User taps 补上 | Set to `daysMissed`. App advances one day per tap, decrementing counter. |
| Counter reaches 0 | The field is deleted from state (removed, not set to 0). Streak restored. |
| User closes app mid-catch-up | Counter stays in state. On next app load, `detectMissedDays()` runs again — the catch-up days since `last_active_date` are re-detected. The stale `catchup_days_remaining` is **cleared** and replaced by re-computation. See `cleanupCatchupState()` below. |

```javascript
function cleanupCatchupState(state):
    // Called on app init, before detectMissedDays().
    // Purges any stale catch-up state from a previous interrupted session.
    if state.progress.catchup_days_remaining is not undefined:
        // If there's stale catch-up state, the learner didn't complete it.
        // The streak was already lost — remove the transient and let
        // detectMissedDays() re-compute from scratch.
        delete state.progress.catchup_days_remaining
```

## 6. SRS Specification

### 6.1 SRSItem Type

```typescript
interface SRSItem {
    id: string;           // word ID, e.g., "hsk1_0001"
    word: string;         // Chinese characters, e.g., "你好"
    pinyin: string;       // pinyin with marks, e.g., "nǐhǎo"
    english: string;      // English meaning
    level: number;        // HSK level (1-9)
    ease: number;         // SM-2 ease factor, default 2.5, min 1.3
    interval: number;     // days until next review
    nextReview: number;   // timestamp (ms) of next review
    repetitions: number;  // consecutive correct reviews
    lastWritingScore: number | null;  // totalMistakes from last hanzi-writer quiz
}
```

### 6.2 ensureEnrolled() — Auto-Enrollment

```javascript
function ensureEnrolled(words):
    items = loadSRS()
    known = new Set(items.map(i => i.id))
    changed = false
    for w in words:
        if known.has(w.id): continue
        items.push({
            id: w.id,
            word: w.word,
            pinyin: w.pinyin_text,
            english: w.english,
            level: w.hsk_level,
            ease: 2.5,
            interval: 0,
            nextReview: Date.now(),  // immediately due
            repetitions: 0,
            lastWritingScore: null
        })
        known.add(w.id)
        changed = true
    if changed: saveSRS(items)
```

Called on 识 phase entry with the day's word (array of 1 item).
Insert-if-absent: never resets existing ease/interval.

### 6.3 getDueItems() — Review Queue

```javascript
function getDueItems():
    now = Date.now()
    return loadSRS().filter(item => item.nextReview <= now)
```

Returns items sorted by `nextReview` ascending (oldest due first).
The 习 phase shows up to 4 items per session.

### 6.4 recordResult() — SM-2 Core

```javascript
function recordResult(wordId, quality):  // quality: 1 = "需要再背", 4 = "会了"
    items = loadSRS()
    idx = items.findIndex(i => i.id === wordId)
    if idx == -1: return

    item = items[idx]
    if quality >= 3:
        item.repetitions += 1
        item.interval = Math.round(item.interval * item.ease)
        if item.interval == 0: item.interval = 1
    else:
        item.repetitions = 0
        item.interval = 1

    item.ease = Math.max(1.3, item.ease + (0.1 - (5 - quality) * 0.08))
    item.nextReview = Date.now() + item.interval * 86400000

    items[idx] = item
    saveSRS(items)
    recordActivity()
    incrementDaily("reviews_done")
```

**Quality values used in 每日字:**
- `1` — "需要再背" (need to revisit) — resets interval to 1 day
- `4` — "会了" (I remember) — grows interval by ease factor

The full SM-2 quality range (0–5) is available for future quiz modes (v2).

### 6.5 Writing Score Integration

When the 写 quiz completes with `totalMistakes`:

```javascript
function recordWritingScore(wordId, totalMistakes):
    items = loadSRS()
    idx = items.findIndex(i => i.id === wordId)
    if idx == -1: return
    items[idx].lastWritingScore = totalMistakes
    saveSRS(items)
```

In v2, it can be used to bias the review queue: words with high writing mistakes

## 7. Audio Specification

### 7.1 Edge TTS Configuration

- **Tool:** `edge-tts` Python library (free, no API key required)
- **Voice:** `zh-CN-XiaoxiaoNeural` (晓晓, Chinese female)
- **Speed:** `0.95` (5% slower — better for language learners)
- **Format:** `mp3`
- **Cost:** Free. Uses the same backend as the Edge browser "Read Aloud" feature — no rate limits, no API keys.

### 7.2 Audio File Structure

```
audio/
├── index.json
└── word_audio/
    ├── hsk1_0001/
    │   ├── word.mp3        ← "你好"
    │   └── sentence.mp3    ← "你好，我是小明。"
    ├── hsk1_0002/
    │   ├── word.mp3
    │   └── sentence.mp3
    └── ...
```

### 7.3 Audio Generation Script

`scripts/generate_audio.py`:

```python
#!/usr/bin/env python3
"""Generate audio for HSK words using Edge TTS."""

import asyncio, json
from pathlib import Path

import edge_tts

VOICE = "zh-CN-XiaoxiaoNeural"
RATE = "-5%"  # slowed down by 5% for learner clarity

async def tts(text, out_path):
    communicate = edge_tts.Communicate(text, voice=VOICE, rate=RATE)
    await communicate.save(out_path)

async def main():
    hsk = json.loads(Path("data/hsk_daily.json").read_text())
    index = {"version": 1, "files": {}}
    audio_dir = Path("audio/word_audio")

    tasks = []
    for word in hsk["words"]:
        wid = word["id"]
        out_dir = audio_dir / wid
        out_dir.mkdir(parents=True, exist_ok=True)

        word_mp3 = out_dir / "word.mp3"
        sent_mp3 = out_dir / "sentence.mp3"

        if not word_mp3.exists():
            tasks.append(tts(word["word"], word_mp3))
            print(f"  queued: {wid} word")

        if word.get("example", {}).get("zh") and not sent_mp3.exists():
            tasks.append(tts(word["example"]["zh"], sent_mp3))
            print(f"  queued: {wid} sentence")

        index["files"][wid] = {
            "word": str(word_mp3.relative_to(Path("audio"))),
            "sentence": str(sent_mp3.relative_to(Path("audio")))
        }

    if tasks:
        print(f"Generating {len(tasks)} audio files...")
        await asyncio.gather(*tasks)
        print("Audio generation complete.")

    Path("audio/index.json").write_text(json.dumps(index, ensure_ascii=False, indent=2))
    print(f"Done. Index written for {len(index['files'])} words.")

if __name__ == "__main__":
    asyncio.run(main())
```

```javascript
        audio.playbackRate = settings.audio_speed
        audio.play()
        return
    // 2. Fallback: show "audio unavailable"
    showAudioUnavailable(wordId)
```

**`showAudioUnavailable(wordId)` behavior:**
1. The play button is greyed out (`opacity: 0.4, pointer-events: none`).
2. The label text changes from "▶ 听" to "音频 未生成" (audio not yet generated).
3. The `title` attribute is set to "运行 scripts/generate_audio.py 生成此音频"
   (run generate_audio.py to produce this audio).
4. The button remains visible but non-interactive — no tooltip toast, no modal,
   no disruptive error. The app simply acknowledges the audio isn't ready.

The frontend loads `audio/index.json` once on init. If a word's audio is not in the
index, the play button shows "音频 未生成" — the full set can be batch-generated by running `scripts/generate_audio.py`.

**Subpath deployment note:** Audio paths in the index are relative to the `audio/`
directory (e.g., `word_audio/hsk1_0001/word.mp3`). When constructing the full URL,
the frontend must prepend the site's base path. For GitHub Pages subpath deployment
(e.g., `username.github.io/mei-ri-zi/`), compute the URL as:
```javascript
const base = location.pathname.replace(/\/+$/, '')  // strip trailing slash
const audioUrl = `${base}/audio/${entry[type]}`
```

## 9. Export / Import / Sync

### 9.1 Option A — Backup File

```javascript
function exportBackup():
    state = loadState()
    blob = {
        schema: "mei-ri-zi/export",
        schema_version: 1,
        app_version: "1.0.0",
        exported_at: new Date().toISOString(),
        state: state
    }
    json = JSON.stringify(blob, null, 2)
    downloadFile(json, `每日字-progress-${todayISO()}.json`, "application/json")

function importBackup(file):
    text = await file.text()
    blob = JSON.parse(text)
    if blob.schema !== "mei-ri-zi/export" or blob.schema_version !== 1:
        throw new Error("Invalid backup file")
    saveState(blob.state)
    location.reload()
```

### 9.2 Option B — Sync URL

```javascript
function createSyncURL():
    state = loadState()
    json = JSON.stringify(state)
    compressed = gzip(json)                    // pako or similar
    encoded = btoa(String.fromCharCode(...compressed))
    return `${location.origin}${location.pathname}#sync=${encoded}`

function loadSyncURL():
    hash = location.hash
    if not hash.startsWith("#sync="): return false
    encoded = hash.slice(6)

    try:
        decoded = atob(encoded)
        bytes = new Uint8Array([...decoded].map(c => c.charCodeAt(0)))
        json = gunzip(bytes)
        state = JSON.parse(json)
    catch:
        alert("同步链接无效 / Invalid sync URL")
        return false

    saveState(state)
    location.hash = ""  // clear fragment
    location.reload()
    return true
```

**Notes:**
- No encryption. HSK vocabulary progress is not sensitive data — see plan §4.4 "Why localStorage is sufficient."
- This removes the entire class of forgotten-passphrase / lost-key failure modes.
- The `gzip`/`gunzip` helpers use the `pako` library (or equivalent) loaded from CDN.
- The URL fragment is **never sent to the server** (everything after `#` is client-side only) — so the static host never sees the state, even in plain text.
- A ~5KB state blob compresses to ~2KB gzip, then ~2.7KB base64. Well within URL length limits for all modern browsers (>2MB).

```javascript
function gzip(str):
    // pako.gzip(string) returns Uint8Array
    return pako.gzip(str)

function gunzip(bytes):
    // pako.ungzip(uint8array) returns string (with {to: 'string'})
    return pako.ungzip(bytes, { to: 'string' })
```

### 12.2 Atmospheric Effect

The `temp` value (0.0 = deepest winter/ink, 0.8 = peak summer/warm) follows the
**philosophical yang-shading curve**, not average temperature. In Chinese cosmology,
夏至 (summer solstice) is the peak of yang energy — after which yin begins its
return. This is why 夏至 has the highest `temp` value (0.8) even though the
hottest weather (三伏天) arrives later. The curve encodes philosophical seasonality,
not climatological heat. Do not "correct" 大暑 to be warmer than 夏至.

The `temp` value controls:
- Background tint: `hsl(220, 15%, ${4 + temp * 4}%)` — subtle shift from deep ink to slightly warmer
- Card border opacity: `0.05 + temp * 0.1` — slightly more visible in summer
- The solar term name displayed in the header (§10.1)

This is deliberately subtle — atmosphere, not wallpaper.

### 12.3 Solar Term Resolution (cross-year wrap)

Since 小寒 and 大寒 (January) fall after 冬至 (December) in the calendar year,
a simple "closest preceding term" scan must handle the year boundary correctly:

```javascript
function getCurrentSolarTerm():
    now = new Date()
    todayMD = now.getMonth() * 100 + now.getDate()  // e.g., Feb 4 → 204

    // Find the most recent solar term whose (month, day) is <= today.
    // Handle January dates by checking if the term falls before Feb 4 (立春):
    // if today is before 立春, use the *previous year's* 小寒/大寒 instead.
    lastTerm = null
    for term in SOLAR_TERMS:
        termMD = term.month * 100 + term.day
        if termMD <= todayMD:
            lastTerm = term
    
    if lastTerm:
        return lastTerm
    else:
        // today is before 立春 (Jan 1 – Feb 3). Return 大寒 from "previous year"
        // — which is just the last entry in the SOLAR_TERMS array.
        return SOLAR_TERMS[SOLAR_TERMS.length - 1]
```

The key insight: the array is ordered chronologically through the solar year,
starting from 立春 (Feb 4). January terms (小寒, 大寒) sit at the end of the
array. The `else` branch catches Jan 1 – Feb 3 by fetching the last entry (大寒).

## 15. Cultural Sensitivity Audit

Run this checklist before any public deployment. Use the taboo rules from the
`traditional-chinese-design` skill as the reference.

### Pre-Ship Checklist

| # | Rule | Check | Notes |
|---|------|-------|-------|
| 1 | **No green headwear** — green hats/badges/accents on person-like
    illustrations are a pun for cuckoldry (绿帽子). | Confirm no avatar, mascot,
    or guardian illustration wears green on the head. Our guardians are ink-wash
    SVGs with no human figures, so this is low-risk — but check the Azure Dragon
    (青龙) SVG for any crown/halo that could read as headwear. |
| 2 | **No red names** — writing names in red signifies death / a final parting.
    Ensure no learner-facing text uses red as foreground color for names.
    Tone-4 pinyin (vermillion `#d4654d`) is acceptable because it signals a
    linguistic tone, not a person's name — but the `aria-label` should	ext
    include "fourth tone" to disambiguate for screen readers. |
| 3 | **No white-dominant celebrations** — white is the color of mourning.
    The 甲子 celebration uses gold accent on dark background (not white
    dominant). The level-transition guardians use their element colors
    (red, green, silver, blue), not white. |
| 4 | **Four is not displayed prominently** — 四 (sì) sounds like 死 (death).
    We don't use 4 as a prominent number anywhere in the UI (no "Step 4",
    no "Day 4" in the badge — we use stem-cycle labeling instead). The
    HSK levels are labeled 1-9, which is fine. |
| 5 | **No upside-down characters** — unintentional inversion of auspicious
    characters (especially 福) is bad luck. Confirm no Chinese character in
    the UI is rendered upside-down, even in decorative illustrations. |
| 6 | **Wu Xing colors are used correctly** — confirm no element is assigned
    to the wrong direction (Wood=East=green, Fire=South=red, Center=yellow,
    Metal=West=white/silver, Water=North=black/blue). The altar band colors
    must match the 社稷坛 arrangement precisely. |

### Post-Ship Monitoring

- Collect user feedback on color choices (GitHub Issues or anonymous survey).
- If a Chinese-native learner reports a cultural concern, treat it as P1.
- The `traditional-chinese-design` skill may be updated with new taboo rules;
  re-run this checklist before any major version bump.
